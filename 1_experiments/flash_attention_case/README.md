# 工具的第一个完整案例：Triton 教程的 flash attention

日期：2026-10-13。对象：Triton 3.6.0（`ka_main`），RTX A6000（sm_86）。

## 目的

用一个真实、常见的算子检验工具能不能被当作审查工具使用：写好一个 Triton 算子、给一次代表性输入（可选地给一个规格），
工具能不能说出有没有系统偏差、来源在哪一行、是什么机制、怎么改，判断不了的地方能不能明确说判断不了。过程中发现的工具缺陷
就地补上，每处先写修复前失败的测试。第二轮按一份从开发者视角写的审阅改报告（见「报告」与「第二轮」两节）。

## 材料

- `tutorial_fwd.py`：Triton 3.6.0 教程 `06-fused-attention.py` 的前向 kernel，逐字搬来（MIT 许可，SHA-256 e37baf30…；
  下载件放在 `.cache/untrusted/`），只去掉 autotune，用教程自己测试的配置（BLOCK_M 128、BLOCK_N 64、2 stages、4 warps）；
- `make_planted.py` → `planted_fwd.py`：在教程源码上逐行植入一处缺陷的四个变体：

| 变体 | 植入的缺陷 | 性质 |
|---|---|---|
| tf32 | fp32 输入，两个 `tl.dot` 用默认 tf32 | 数值 bias（操作数截断） |
| scale | `qk_scale *= 1.44`（应为 1.44269504） | 语义 bias：声明的程序不是规格 |
| l_bf16 | softmax 分母 `l_i` 在循环里保留为 bf16 | 低精度累加 |
| acc_fp16 | 输出累加器用 fp16 | 张量核 fp16 累加器，不在下降规则内 |

- 用法（`audit_fa.py`）：一次调用

  ```python
  audit(launch, spec={"desc_o": lambda: reference}, names={"desc_o": "O", "M": "M（logsumexp）"})
  ```

  其中 `launch` 运行 kernel，规格是 torch 的 float64 注意力。
  - 输入为标准正态，Z=1、H=2、head_dim 64；N = 1024（l_bf16 为 2048、BLOCK_N 16）。
  - program 按工具的默认抽样：各轴首尾 program（含序列末尾的边界块）另加中间两个，16 个中抽 6 个（l_bf16 32 个中抽 6 个）；
    归因用同一组 program。
- 输入与规格的构造在 `fa_inputs.py`。
- 报告在 `results/audit_*.txt`，数据在同名 `.json`：
  - `audit_planted_l_bf16_all.*` 是全部 32 个 program 的审查，`audit_planted_l_bf16_N8192.*` 是 N = 8192 的强停滞；
  - 各 program 分别测得的偏差在 `results/per_program.json`（`per_program.py`）。

另外：

- **M（logsumexp）**：在 tf32 与 l_bf16 中也被报为显著，分别为 −0.0095% 与 −0.028%（未给规格，相对声明的程序），
  来源与 O 相同，改法一并给出。
- **常用容差检查**（对规格）：
  - Triton 教程测试用的 `assert_close(atol=1e-2, rtol=0)` 在所有案例中都通过，tf32、l_bf16、scale 的偏差全部漏掉；
  - `allclose(rtol=1e-2, atol=1e-5)` 与 `assert_close` 的 dtype 默认值在所有案例中都不通过，包括未改动的教程，而且去掉系统
    分量后仍不通过。也就是说，它们被随机误差打破，说明不了偏差。
  - 这三种常用检查都分辨不出 0.1%～0.3% 的系统偏差。
- **l_bf16 的抽样**：
  - 32 个 program 逐个测得的偏差：首尾两个 program 是 +0.069% 与 −0.008%，其余在 +0.16% … +0.47% 之间；
  - 全部 32 个合起来是 +0.29%，抽样的 6 个是 +0.23%；
  - 报告据此提示「各 program 的偏差差别大，抽查值不一定代表整个 kernel，要全量评估传 `programs="all"`」；
  - 用 `programs="all"` 跑的整次审查（`results/audit_planted_l_bf16_all.*`）：
    - 实测 +0.291%（标准误 0.0039%），事前预测 +0.278%，逐位全部相同；
    - 归因到 `:352` 的贡献 +0.291%，改后（模型内）−0.0002%；M 为 −0.036%，改后 <0.0001%；
    - 这次运行早于容差检查的三分类，报告里的容差一句还是旧写法；
  - tf32 的 16 个 program 在 −0.151% … −0.136% 之间，全部与抽样都是 −0.142% / −0.143%。
- **l_bf16 在 N = 8192 时停滞很强**（`results/audit_planted_l_bf16_N8192.*`，program 0）：
  - 实测 O 偏大 +15.5%（标准误 0.29%），M 偏小 −1.5%，逐位全部相同；
  - 事前预测报「无法判断：84% 的元素预测相对误差超过 2⁻⁴」（照算是 +13%）；
  - 预测放弃不影响审查：归因仍给出 `:352` 贡献 +15%，改后（模型内）−0.0001%；
  - 教程自带的 `atol=1e-2` 测试在这里会因为偏差报错。

## 报告

植入 tf32 的报告开头（全文 `results/audit_planted_tf32.txt`，技术细节在其附录）：

```
══ _attn_fwd_tf32：输出 O 系统性偏小约 0.14%（不是噪声）；输出 M（logsumexp） 系统性偏小约 0.0095%（不是噪声） ══

O：系统性偏小约 0.14%（不是噪声）
  · 常用容差检查：assert_close(atol=1e-2, rtol=0)（Triton 教程的测试） 会通过——这个偏差会被漏掉；allclose(rtol=1e-2,
    atol=1e-5)、assert_close 的 dtype 默认值 去掉这个偏差也通不过（随机误差已超出），说明不了它。
  · 运行前预测偏小约 0.14%，实测偏小约 0.14%，一致。
  · 各 program 的偏差在 −0.15% 到 −0.14% 之间，差别在随机误差范围内。
  · 公式与规格一致，问题出在数值实现。
（M 一段略）

原因
  - planted_fwd.py:45  `qk = tl.dot(q, k)`
      tf32 张量核 dot 把两个操作数向零截断到 11 位（每个操作数约 −0.035% 的系统收缩），累加也向零截断；贡献：O −0.075%，M（logsumexp） −0.0095%
  - planted_fwd.py:75  `acc = tl.dot(p, v, acc)`
      tf32 张量核 dot 把两个操作数向零截断到 11 位（…）；贡献：O −0.067%
  - 其他位点合计：O +0.00078%，M（logsumexp） <0.0001%，可忽略

建议
  1. tf32 张量核 dot 的操作数截断（planted_fwd.py:45、planted_fwd.py:75）
     - 各处在 tl.dot 前把操作数用 cvt.rna.tf32.f32 就近取到 tf32：保留张量核，几乎不增加耗时；剩下张量核累加的截断（约 1e-5 量级）
     - 各处改用 input_precision="ieee"：同样消除偏差，但不再用张量核，通常慢数倍
     预测效果，全部 2 处都改：O −0.14% → <0.0001%；M（logsumexp） −0.0095% → <0.0001%
       只改 planted_fwd.py:45：O → −0.068%；M（logsumexp） → <0.0001%
       只改 planted_fwd.py:75：O → −0.075%；M（logsumexp） → −0.0095%
  （预测效果是模型内的反事实：这些位点不再引入误差时的偏差，在同一组 program 上算得；修改后再跑一次 audit 即可在 GPU 上核对。）

数值偏差是否值得修，取决于它进入下游（例如训练）后会不会超过随机种子之间的波动；这需要下游测量，工具不判断。

范围：Triton 3.6.0 / sm_86（锁定的下降规则），抽查 6/16 个 program（规则：各轴首尾 program，含序列末尾的边界块，另取中间 2 个）。
```

scale 的报告标题是「输出 O 比规格偏小约 0.2%（公式或常数与规格不一致）」，并说明数值误差部分（−0.0005%）可忽略、公式或
常数的偏差应当修正，但工具不能定位到具体的常数。acc_fp16 的标题是「实测未发现显著偏差，但事前预测、逐位核对与归因没能完成」，
「无法判断」一节写出不在规则内的 dot（f16 x f16 -> f16）。

## 第一轮：发现并修复的工具缺陷（都先写修复前失败的测试，`2_tool/tests/`）

1. **对 `tl.dot` 输出的归约不可仿真**（`layouts.py`）。softmax 的行最大值与行和作用在张量核累加器布局（nvidia_mma v2）上，
   原来只认 blocked / slice 布局，逐位核对一个元素都仿真不了，预测器也因「归约次序未知」放弃。现在由寄存器 / lane / warp
   的线性基给出沿轴的组合次序（`linear_bases`、`linear_axis_params`），三种形状逐位通过。
2. **近似函数的下溢被当作「格外」**（`bias_predict.py`）。causal mask 的 logit 加 −1e6 后进 exp2，结果在 f32 里是 0，设备也
   给 0；原来因输入落在契约表范围外而放弃。现在精确结果低于正规数范围的通道按冲零确定。
3. **归因看不到张量核 dot**（`emulate.rounding_nodes`）。候选节点只列了早期的几种下降方式，tf32 flash attention 的报告里
   −1.44e-3 的来源完全缺失。现在列入所有舍入的下降方式（张量核 dot、扫描次序、设备组合的归约与扫描、整数转浮点、
   libdevice 精确求值、FTZ）。
4. **不在规则内的 dot 的提示有误导**（`emulate.py`、`bias_predict.py`）。fp16 累加器的 dot 被报成「tensor-core dot (tf32)」
   与「dot (tf32, f16)」；现在写出元素类型。
5. **fp32 fma 链与张量核契约的状态传播**（`bias_predict.py`，外部审阅指出）。原来用精确前缀推进累加器，被舍入吞掉的增量
   在下一步又被算了一次（审阅反例 1 + 3×2⁻²⁴：预测 −1×2⁻²⁴，真实 −3×2⁻²⁴）。现在用设备值估计（精确前缀加已预测的均值误差）。
6. **没有审查入口**：新增 `reference_eval/audit.py`，一次调用完成事前预测、逐位核对、精确参照、逐节点归因与规格对比。

## 第二轮：开发者视角的审阅之后

审阅的意见是：报告里的数没有翻译成人话；没说常用测试会不会放过偏差；没说改法的代价；只给了改一处的效果；抽样规则没说明，
也必须包含序列末尾带屏蔽的块。改动如下（测试在 `2_tool/tests/test_reference_eval_audit.py`）：

- **报告结构**：
  - 开头是给作者的摘要，每个输出一段：偏差多大、是不是噪声、事前预测与实测是否一致、公式与规格是否一致；
  - 原因按源码行列出，带代码、机制和对各输出的贡献；
  - 改法按机制合并（跨输出），每条写明代价；
  - 技术细节（K − G、G − S、标准误、逐节点贡献）移到附录。
- **常用容差检查**：在 K 上，也在去掉系统分量的 K 上算，分成三类：会通过（偏差被漏掉）、因为偏差而报错、去掉偏差也通不过
  （随机误差已超出，说明不了偏差）。没有第三类时，「会报错」会被误读为「检查能发现这个偏差」。
- **改法的效果**：
  - 「全部位点都改」来自一次所有位点同时精确的仿真，不是单点效果相加；也给出只改一处的效果。
  - tf32 两处都改后是 <0.0001%。上一版按单点效果相加得到「约 +0.001%」，那个数不准。
- **抽样**：
  - 默认取各轴首尾 program 加中间两个，包含边界块，范围一节写出规则；`programs="all"` 全量。
  - 报告给出各 program 偏差的范围，并按各自的标准误判断差别是否超出随机误差。
- **缺陷：归因与测量用的不是同一组 program**。归因原来只用前两个 program，修复后的值却是拿全部抽样 program 的实测值减出来的。
  l_bf16 的两个归因 program 正好是偏差小的首尾两个，报告写成「+0.23% → +0.2%」；在同一组 program 上实际是
  +0.23% → <0.0001%。现在归因默认用全部抽样 program。
- **放弃时的标题**：acc_fp16 原来的标题是「未发现需要处理的系统偏差」；现在写明事前预测与逐位核对没完成。
- **下游**：只写「是否值得修取决于下游」，工具不判断；公式或常数与规格不一致时写「应当修正」。

## 能说什么

- 对教程 flash attention 及植入的三类缺陷（数值截断、语义常数、低精度累加），工具在一次调用里给出了正确的判断、来源行、
  机制和改法，事前预测与实测一致；超出模型的部分（fp16 累加器、强停滞）如实报「无法判断」并写明原因。
- 三种常用容差检查在这里都分辨不出 0.1%～0.3% 的系统偏差：宽的放过它，窄的被随机误差打破。
- 改法后面的数字是**模型内反事实**（该位点精确时），不是运行修改后的 kernel；TF32 matmul 上同类修改已有事前预测并经设备
  证实的先例（`../composition_study/README.md` 第 10 节）。

## 局限

- 默认只评估一部分 program；l_bf16 表明 program 之间可以差很多（报告会提示，但抽样值本身仍有偏）。只有一种输入分布
  （标准正态）。只做了前向，没有做反向；反向用原子累加 dQ 时会报「无法判断」。
- 用时：N = 1024 时 6 个 program 的一次审查约 4～7 分钟，包括预测、逐位核对和每个舍入节点一次归因仿真（6 个审查同时
  在 3～4 块 GPU 上跑，仿真主要占 CPU）；l_bf16（N = 2048、BLOCK_N 16）约 17 分钟。大规模输入需要抽样。
- 语义偏差（G − S）只能说「公式或常数不一致」，不能定位到具体的常数或行。
- 改法是按机制的规则给出的，不会自动改写源码；「贡献」由逐点替换得到，不同位点之间有相互作用，相加只是近似（「全部都改」
  的效果是一次仿真算的，不受此影响）。
- 理论层（契约定义、组合定理与余项界）仍未写出，显著性判断与容差是经验的（见 `../composition_study/README.md` 10.4 节与外部
  审阅）。
- 只对 Triton 3.6.0 / sm_86 / 记录的编译选项成立。
- 还没有在未改动的公开实现上试过（审阅建议的下一步）。

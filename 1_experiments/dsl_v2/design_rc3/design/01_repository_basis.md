# 01 仓库是迁移起点，不是DSL边界

本稿以用户上传rc2及其锁定的 `kernel-analyzer@5b9ac32` 为仓库基线。本轮没有重新审计生产代码、没有修改仓库。

## 1. 保留现有核心

rc2描述的 `Program/Op` 已支持SSA值、属性与嵌套区域，求值器已有参照内存、区间、结果类别和模式划分。
继续使用这些结构；补类型、效果、前提、能力和官方来源字段，不另造一门要求用户重写kernel的语言。

没有独立任务规格时，f 缺失就是任务语义未检验；模式A仍可测相对声明计算的数值差。
历史 K_R 字段继续保留，明确它表示目标G、普通对照K0还是包围R。

## 2. 从旧代码迁移什么

| 现有组织 | 应当升级为 |
|---|---|
| 按操作名映射 | 官方版本+op+类型+属性+区域+效应签名 |
| 注册表的SUPPORTED | 语义已定义、实现完成、验证范围分别登记 |
| Welford/scan写法识别 | 通用区域解释+适用的代数或次序证据；模板仅为可退回的优化 |
| 同步nop、按program记录写入者 | 地址空间、线程/warp/CTA/cluster/system作用域和事件关系 |
| 位级中断/实际值回填 | 显式Real/Format/BV桥，或明确外部边界 |
| 只处理TTIR | 经典和Gluon各导入器，共用参照核心与查询层 |
| NaN、未建立、精度不足混排 | 执行状态、语义范围、包围精度与统计条件正交报告 |

有文档语义的官方功能未实现，留在目标清单中。未定义行为不是实现缺口；无法验证前提也不是已经证明程序错误。

## 3. 229和165的正确用途

旧229项来自仓库的名字探针；rc2又将其中一部分移出TTIR分母，得到165。两者都只能用于复算历史记录。
旧64项不再从官方总目标删除，而按host、低层或验证角色分别登记；是否被某个前端/构建实际使用，由官方源码、安装注册和编译记录三方核账。

`coverage/legacy_229_route.json` 保留所有旧条目与历史映射，不代表当前官方全集，也不代表新版已经实现。

## 4. 两条不能遗漏的前提

1. 整数仍需位宽、溢出标志、poison、除零规则；“整数精确”不等于任意标志组合总有值。
2. 位级操作走格式桥，不回填实际值；以Format保留某段舍入时，必须公开哪些误差不再进入K−G。

# 规格 v3 计划（2026-10-16 登记，执行之前）

## 0 为什么有这一版

用户定的两条底线：

1. 审稿人不会觉得我们随便设置了某个规格；
2. 我们测过的算子都要有规格，不能存在未定义的情况。

2026-10-16 的外部审阅（[REVIEW.md](../reviews/2026-10-16/REVIEW.md)）提出三道关：语义有依据、参照可信、与 kernel 对得上。
审阅指出的事实已经复核属实：
- **检查器假通过**：
  - 期望值改错，检查器报出矛盾但退出 0；
  - 替代读法改错，仍显示 54/54 成立；
- **10-16 包的版本**：带的是 10-15 的旧草案合同和旧检查器；
- **参照代码的错误**：
  - 三个相等 logit 下，MoE 权重区间不含 1/3；
  - 两个参与者只给一份权重，加权归约静默返回；
  - 线性注意力递推与分块的默认缩放不一致。

这一版采纳三道关，但把范围从 v2.5 的陌生库清点改为**我们测过的算子**。

**用户的决定（2026-10-16）**：
- 范围按测过的算子，不含 library survey 的 797 个分族；
- 合同由执行方（Claude）起草并负责；
- v2.5 除覆盖测过算子的几份以外，退到草案区，不进任何结论。

## 1 范围：测过的算子

分母是清点表 `corpus/tested_operators.json`，在第 2 阶段生成，在写任何新合同之前冻结。冻结之后只能加、不能删。

每一项归入三类之一：

| 类别 | 含义 | f 从哪来 |
|---|---|---|
| T | torch 算子与组合：本质错误轮与收束轮的 15 个家族、通用轮 15 个回归案例、容差研究、flash attention、three_way 的 Inductor kernel、组合研究的 Liger / FlagGems 语料 | 算子合同；编译 kernel 由 Inductor 写在生成代码里的 ATen 计算图片段组合；手写 kernel 按它替换的 torch 接口对应 |
| I | 出题方定义的程序：盲测 v1、v2，结构验收 v1.1 | 出题方的公式，身份标为「任务定义（出题方）」 |
| P | 任务就是程序本身：dsl_v2 的官方测试、组合研究的原语与随机程序、第一批验收 | 写明「语义检查不适用」，不算未定义；这些实验只主张 K − G |

不在范围内：
- library survey 的 797 个分族；
- v2.5 中没有覆盖测过算子的合同（退到 `drafts/v2_5/`）。

范围之后的扩展（第 7 阶段）：
- 覆盖 PyTorch Core ATen 算子集（torch 2.10 中 163 个基本算子，分母由 PyTorch 定义）；
- 冻结后的留出检查：编译不在 23 个模型里的新模型，报告不补合同时能完整定义的 kernel 比例。

## 2 两条底线的验收标准（事先定，结果只写成立 / 不成立 / 无法判断）

### V1 检查器能传播失败（第 1 阶段）

以下每一种注入都必须让总检查返回非零，正常合同必须通过。注入先写成失败的测试，再修代码：

| 编号 | 注入 |
|---|---|
| A | 期望值改错 |
| B | 依据改成不存在的来源编号 |
| C | 子测试 exit(9) |
| D | 倒置区间（下界大于上界，差值再小也不行） |
| E | 缺一个输出字段、一个状态字段或一行输出 |
| F | 替代读法的期望值改错 |
| G | 未审阅的合同、未绑定的任务 profile 或过期的哈希被自动启用 |
| H | 只靠抛异常「杀死」的变异 |
| I | 隐藏容差：期望值与真值相差 10⁻⁴⁵（相对）时，精确参照必须判矛盾；包围参照不严格包含时不得判一致 |

### V2 不是随便定的（底线 1）

- **依据**：每条条款解析到 `SOURCES.json` 中带原文快照 SHA-256 的条目，或一条登记的决定。决定要列出全部备选。原文没规定处写成合法读法的集合，只有违反全部合法读法才判矛盾。
- **冻结**：合同在第一次用于 kernel 比较之前入库，提交时间早于运行记录。之后的修改只能由重读原文或独立核对触发，记入合同的 `changes`。
- **旁证**：torch 算子合同与 PyTorch 自己的实现比较（CPU float64 eager，有官方分解的再比分解），在随机输入与边界输入上报告一致率。分歧逐条分拣为规格错、实现错或文档含糊。旁证不签发条款，但可信的矛盾会暂停相关条款。
- **变异**：每条变异要求都执行并记录。被拒绝要有指定输出上的矛盾见证。
- **作者与审阅**：作者是 Claude。外部审阅之前，合同状态为 `drafted`，用它算出的结果一律标「草案合同」。

### V3 测过的算子都有规格（底线 2）

- 清点表的每一项都有类别。T 类与 I 类项都对应到合同和 profile；P 类项写明「语义检查不适用」。
- 对清点表里记录过的每个测试条件，参照只返回三种结果之一：
  - value（含精确值、严格包围、允许集合、声明近似）；
  - domain_undefined（合同写明后果，例如「无要求」）；
  - invalid_input。
- `unsupported`、「无 f」、「契约外」的计数为 0；超出计算预算的 `not_established` 单独列出。
- **three_way 的 Inductor kernel**：
  - 静态：每个单元的计算图片段中，每个运算及其参数都落在某份合同的 profile 里；
  - 动态：随机抽 100 个逐位一致的单元（种子 20261016），在捕获的输入上求出 f，与设备输出 K 比较。

### V4 历史 f 的回放

历史上的 f 有七种来源：
1. 盲测出题方的公式；
2. 结构验收包自带的 f；
3. 旧 phase1 / phase2 副本；
4. 通用轮逐案手写的 float64 参照；
5. 容差研究的手写规格；
6. flash attention 的 torch SDPA float64；
7. three_way 植入时取未改 kernel 的 G。

在原记录的条件上，用 v3 合同重算 f，报告一致与不一致。不一致照实登记，不改冻结的历史记录。

## 3 比较规则（检查器与工具共用）

| 参照 | 期望 | 判定 |
|---|---|---|
| 精确值 | 精确值 | 相等为一致，不等为矛盾 |
| 严格包围 R | 精确表达式 e（用区间算术求出包围 E） | E 与 R 不相交为矛盾；E ⊆ R 为一致（包围）；相交但不包含为未建立 |
| 允许集合 | 集合 | 集合相等为一致，否则为矛盾 |

其余规则：
- 不设任何隐藏容差。高精度点值复算单列为「数值复核」，不计入一致。
- 变异只在至少一个见证例子上与期望矛盾时算被拒绝。抛异常记为「不适用」，不算拒绝。
- 退出码：0 表示全部一致；1 表示有矛盾、结构错误或实现错误；2 表示有未建立。

## 6 偏离

- **D1（2026-10-16，第 1 阶段）**：v2.5 的已知错误参照（MoE 权重区间、加权归约、线性注意力默认缩放等）不在第 1 阶段修，
  改为在第 3 阶段启用对应合同时修。理由：v2.5 已隔离，不被任何入口加载；只有覆盖测过算子的几份会启用，在启用前修可以先写失败测试、
  再修，与其余合同同一流程。已复核的问题清单见 `drafts/v2_5/STATUS.md`。
- **D2（2026-10-17，第 4 阶段，three_way 动态部分）**：计划写的是在 100 个单元上求 f 并与 K 比较，没有写对应关系怎样建立、差异怎样报告。现定：
  - kernel 参数到图输入、输出的对应，只用生成代码里的调用处缓冲区名、图节点名，以及捕获的形状和 dtype，不用数值匹配；
    对不上或有歧义的单元照实报告为「对应未建立」，并写明原因。
  - f 用惰性求值（`kernel_spec/lazy.py`，已用 `tests/test_lazy.py` 逐运算与合同参照核对），每个输出抽 34 个元素。
  - 差异报相对误差 |K − f| / |f|。分两种读法：程序原样，以及 Inductor 默认省略中间转换。fp32-TF32 配置的矩阵乘本来就有约 10⁻³ 的相对误差，
    这是数值偏差，不是语义差异。相对误差达到 O(1) 才提示对应可能有误。

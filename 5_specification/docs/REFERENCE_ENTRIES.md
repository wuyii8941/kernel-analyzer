# 任务定义从哪里来：三步、五个参照入口与独立性原则（2026-10-20）

本文件回答两个问题：

1. 一个实现（kernel、算子、库函数）的 f 从哪里来；
2. 不同来源的 f 各能检查什么。

它不改任何合同语义，只固定口径。路径 A 的实施方案见 `OPERATOR_ENTRY_PROTOCOL.md`。

## 0 原则：参照必须独立于被检查的那一步变换

层越高不一定越好。真正的要求是：**要检查某一步变换（分解、改写、下降、融合）是否出错，f 就不能取自这一步的输出。**

例子：任务是三个数取平均，f(x) = (x₁+x₂+x₃)/3。分解阶段错写成除以 4，得到图 D；编译器忠实地生成 kernel。忽略舍入时
D = Gπ = K = (x₁+x₂+x₃)/4。

| 比较 | 结果 |
|---|---|
| K − Gπ（执行相对程序声明） | 无差异 |
| Gπ − D（程序相对选定的图） | 无差异 |
| D − f_op（图相对独立的算子定义） | **能看到错误** |

在输入、状态和观察范围已经对齐时：

    K − f_op = (K − Gπ) + (Gπ − D) + (D − f_op)

工具不必每次都算齐三项。只要 f_op 与实际输出的对应可靠，就可以先检查 K − f_op。

「图层查不出图的改写错误」并不是无条件成立的。如果参照图保存在错误改写**之前**，它仍然能检查后续的改写。
真正的盲区是：**把可能已经出错的图，当作它自己唯一的参照。**

## 1 三步：按实现声称自己是什么来取得 f

规格不由被测实现的代码定义，而由它**声称自己实现的东西**定义。

| 步骤 | 实现声称 | f 的来源 | 人工 | 例子 |
|---|---|---|---|---|
| **第一步** | 它是某个 ATen 算子的某个 overload | 该 overload 对应的已准入合同，按完整的 overload、参数、dtype、shape 判定唯一适用的 profile | 基本不需要；需要任务选择时转入第二步 | FlagGems 用 `torch.library` 替换 `aten.addmm`；Inductor 编译 `aten.avg_pool2d_backward` |
| **第二步** | 它实现某个已知功能，但不是某个现成算子 | 现有角色合同（NORM、CE、ATTN…）或基础合同的组合，加上任务声明（选哪个 profile、哪种读法） | 规格匹配：可以自动给出候选，由人确认 | Liger RMSNorm、cce 的融合线性交叉熵、vLLM paged attention |
| **第三步** | 什么都不声称 | 无 | 不做 | 作者自创、没有任何声明的算子 |

第三步不做语义判断，结论写「无法判断」，只报告程序层的 K−Gπ（执行相对程序自己的声明）。
如果作者提供了参考实现，可以把它当作 f，但报告必须写明「f 来自作者的参考实现」。这时检查的是「实现与参考是否一致」，
不是「参考是否正确」。

## 2 五个参照入口（不是能力阶梯）

五个入口回答的是「f 从哪里取得、对应到什么」。它们之间**不是逐层包含**的关系：高层只检查最终输出时，
内部误差可能互相抵消，也可能发生在没有观察的状态上。

| 参照入口 | 主要检查的承诺 | 不能省略的条件 |
|---|---|---|
| **过程 / 状态序列** | 多次调用共同实现的状态演化，是否符合任务要求 | 说明观察哪些状态、哪些步骤；范围大不等于没有盲区 |
| **公开调用** | 接口承诺的完整输出、梯度和状态 | 版本、参数与实际计算区域必须匹配 |
| **标准算子** | 某个具体 overload 的数学语义与状态语义 | schema 帮助自动传参，但不能代替数学合同 |
| **逻辑图 / 编译图** | 选定的图所表达的组合计算 | 说明图位于哪些变换之前，是否独立于待查的错误 |
| **kernel 程序** | 程序声明（Gπ）与实际执行的关系 | 依赖 DSL、导入和执行模型的适用范围；不推断没有提供的任务意图。Gπ（声明参照）与逐位执行模型（解释设备行为）承担不同义务，不合并 |

三步与入口的关系：
- 第一步走标准算子入口；
- 第二步走公开调用入口或过程入口；
- 第三步只剩 kernel 程序入口。

逻辑图 / 编译图入口用来组织和求值独立任务（GRAPH 的组合能力）。只有当图的位置早于待查的变换时，它才算独立参照。

## 3 已知缺陷怎么写

不写「某个缺陷最低必须到哪一层才能发现」，这是没有证明过的分类定理。写三件事：

- **本次用哪个入口发现**；
- **需要什么触发条件**：前一次调用、特定数值、特定布局；
- **验证到了什么后果**：一次更新的差，或长期累积的影响。

例子：
- 一次状态更新就可能发现低精度 EMA 丢掉了增量；证明长期停滞，才需要跨步观察。
- 跨调用缓存错误可能需要前一次调用来触发；但错误一旦发生，当前调用的参数与输出就可能足以暴露不一致。

## 4 运行时记录的限制（第一步实施时必须守住）

- **记录器不能换掉被测程序。** PyTorch 2.10 的 `TorchDispatchMode`：
  - 默认（`ignore_compile_internals()` 为 False）时，`torch.compile` 通常退回 eager；
  - 设为 True 时，保留编译执行，但融合在内部的算子不会逐个交给 mode。

  所以，加了记录器之后得到的高覆盖率，不能算作原 Inductor kernel 的覆盖率。仓库的 `provenance.py` 已经因此把追踪放在
  非测量运行中，并要求追踪到的启动与测量启动对应。
- **记录位置必须早于被检查的变换。** 部分 `CompositeImplicitAutograd` 算子在到达 Python dispatch 之前就已经分解，
  这时 mode 看到的是分解后的结果，不是原算子的独立边界。
- **两条连接都要建立**：
  1. 标准调用 → 正确的合同与唯一的 profile；
  2. 合同的观察点 → 实际执行结果（返回值、后态）。

  融合后不存在的中间张量，不能凭空恢复成「已观测结果」。

## 5 第一步的两条执行路径

- **路径 A：实际运行仍有清楚的算子分派边界。** 例如已注册的算子调用确实进入第三方 Triton 实现（FlagGems）。
  这时可以自动取得 overload、参数、输入前态、返回值和后态，交给已准入的算子合同，直接检查 K−f。
  仍需核验三点：
  - 执行的确实是目标 Triton 实现；
  - 记录时数据没有被转换；
  - 原地修改和所有承诺的输出都没有遗漏。
- **路径 B：Inductor 已把多个算子融合。** 在可疑的分解或改写之前保存任务节点与合同，保留它们到生成代码、缓冲区和
  启动区域的来源对应，然后在实际可观察的完整区域边界上比较。没有单独的 softmax 输出，就检查包含它的完整融合区域；
  不能为了测 softmax 把融合拆掉，再声称原融合 kernel 已通过审查。

  反向同理：要检查反向公式，参照从独立的前向数学定义及其导数要求构造，不能把生成好的候选反向图当作正确导数。
  路径 B 另行设计，本轮不做。

两条路径共用已有的合同、求值器和结果保证，不需要两套 ground truth 理论。

## 6 写进方案的主张

> 我们允许从过程、公开调用、标准算子和逻辑图等入口取得任务定义，并在实际计算区域上建立对应。参照必须独立于待检查的变换；
> 标准 schema 用于减少绑定工作，编译来源用于连接实际执行，二者都不能单独充当正确性证明。

不写：「五层逐层包含」「算子层目前为空」「套上 TorchDispatchMode 就能自动检查所有 Inductor kernel」。

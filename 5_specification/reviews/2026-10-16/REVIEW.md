# Specification 最终需要修改什么，以及为什么

先给一个明确结论：我们现在不缺一套新的 specification 理论，也不需要继续通过增加算子数量来证明 ground truth 合理。真正缺的是一条能够被审稿人逐项核查的正确性证据链。

我重新对照了你 10 月 16 日的规格包、上一版已审阅的 `5_specification`，以及实际代码。当前最大的问题不是公式数量不够，而是：

规格有来源，不代表公式转写正确；公式正确，不代表参照执行器正确；参照正确，也不代表它与正在检查的 Triton kernel 是同一个任务。

所以我建议把整个 specification 的合格标准固定为三个条件：

第一关：语义有依据

为什么这个数学目标就是该 kernel 应当实现的任务？

第二关：参照可信

为什么可执行规格完整、正确地计算了这一数学目标？

第三关：对应关系成立

为什么实际 kernel 的输入、输出、状态与这份规格对应？

三关全部通过，才能把这份规格用于相应范围的语义裁决。任何一关缺证据，都不能用另外两关的测试通过来抵消。

这就是我们接下来所有修改的统一理由。 不再单独发明第四层、第五层规格，也不再把几个开发案例通过当作整个方法可靠的证据。

下面按优先级说明具体需要改的文件、内容和验收标准。

## 一、到底改哪七处？

这里按依赖顺序排列。前五项解决 specification 自身是否可信，第六项解决 Triton kernel 能否正确使用它，第七项解决 怎样向审稿人提供证据。

### 1. 先取消多个规格版本竞争，固定唯一权威入口

优先级 P0 · 涉及 `5_specification/`、`contracts/`、`run_all.sh`

现在的问题： 10 月 16 日包仍带着 10 月 15 日的旧 draft 合同和检查器，而此前整合版本已经有更新的 reviewed 合同。这意味着修过的错误有可能因为包替换重新出现。

具体修改：

以已经审阅的 `5_specification` 为基线，将 `specification_v2_5` 作为增量合并。只允许一个运行时注册入口；历史版本保留，但禁止运行时自动回退到旧 draft。

每份规格绑定来源版本、合同版本、参照代码哈希和审核状态。

为什么必须改： 如果同一个任务能够因导入路径不同得到两个 ground truth，我们连“本次实验使用哪个标准”都无法回答。

验收： 同一合同只有一个有效解析结果；被禁止的旧版本不能被静默调用；切换合同版本必须改变可追溯的规格身份。

### 2. 把“数学任务是什么”精确落实到每份合同

优先级 P0 · 涉及 `METHOD.md`、`specification_v2_5/contracts/*.yaml`

这里不是让 Codex 再写一遍论文，而是要求每个影响答案的语义决定，都有明确依据。

一份合同至少必须固定：

| 字段      | 必须说明的内容                     |
| ------- | --------------------------- |
| 来源      | 标准、论文、框架语义或用户任务定义，包含具体版本与章节 |
| Profile | 当前究竟选用了哪一种合法公式或实现约定         |
| 输入与前态   | 类型、维度、布局、参与者、初始状态           |
| 输出与后态   | 全部被承诺的数值、梯度、状态和内存效果         |
| 允许结果    | 唯一值、集合、严格包围或明确的近似           |
| 未定义与未支持 | 哪些条件根本不能裁决                  |

本轮有两个必须修改的合同。

A1_LINEAR： 当前引用 Katharopoulos 的线性注意力，却主要定义未归一化的 \\(S^\top q\\)。该论文的完整归一化版本还包含 \\(Z\\) 状态和分母。

正确做法不是删掉现有公式，而是将其明确标为 `unnormalized_core`；只有包含归一化和对应状态的 profile 才能声称检查完整的论文算法。

F2_MX： 当前 `ocp_floor` 有标准依据，但 OCP 允许其他转换选择。应把 `ocp_floor` 和 `ceil_pow2` 按明确的选定 profile 区分，而不是把使用另一种合法算法的实现自动判错。

为什么必须改： 我们不能用“某篇论文支持这一计算步骤”，推导出“这一步就是完整任务的唯一答案”。

验收： 每条会影响结果的默认值、公式、布局和状态选择，都能追溯到具体来源或明确任务声明；未选择的合法 profile 不参与错误裁决。

### 3. 让参照执行器完整兑现合同，不能丢输入、状态或输出

优先级 P0 · 涉及 `spec_linear_attention.py`、`A1_LINEAR.py`、`spec_moe_routing.py`、`spec_collectives.py` 及共用输入校验层

这是目前明确存在的错误参考答案问题。

| 当前错误                    | 必须采用的通用修复                | 最小验收                           |
| ----------------------- | ------------------------ | ------------------------------ |
| 线性递推、分块、反向使用不同的默认 scale | 所有路径采用同一个 profile 参数解析规则 | \\(d_k=4\\) 时，三条路径的默认缩放一致      |
| A1 适配器忽略 `S0`，只返回部分输出   | 完整传入前态，返回输出、最终状态及被声明的梯度  | 有 `S0=[[2]]` 的既有例子必须得到 `(5,5)` |
| FusedMoE 矩形下投影输出被截短     | 明确矩阵维度与方向，严格核对全部输出长度     | hidden=2、output=3 必须返回三个坐标     |
| 加权归约丢弃多余参与者             | 在任何计算之前核对参与者、权重及张量形状     | 两位参与者只给一份权重必须拒绝                |
| 非整数计数被截断                | 严格检查输入类型                 | `3.9` 不能作为合法计数                 |

这些都不应通过“针对 A1 增加一个特殊判断”来修。

应该实现的是共同不变量：

> 参照计算只能使用经过验证的输入；不能遗漏合同声明的前态、参与者、输出与后态；不能在结构不一致时返回一个看似合理的部分结果。

为什么必须改： 这类错误会直接制造假的 \\(G-f\\)，进而让正确的 Triton kernel 被报告成存在语义偏差。

### 4. 对严格参照，保证数学值不会在处理过程中丢失

优先级 P0 · 涉及 `spec_moe_routing.py`、`spec_paged_attention.py`、`spec_collectives.py`

这是第二关里最关键的数学保证。

设合同允许的全部正确输出和后态为：

\\[ \llbracket C\rrbracket(x,s). \\]

当我们使用严格包围 \\(\widehat R_C\\) 时，必须保证：

\\[ \boxed{\llbracket C\rrbracket(x,s)\subseteq\widehat R_C(x,s).} \\]

也就是说，参照可以因为不够精确而宽一些，但不能把真正正确的答案排除在外。

这次有两个确定反例。

MoE 权重： 当前把区间端点转成40位小数字符串，再当作数值重建，导致三个相等 logits 下的准确权重 \\(1/3\\) 不在返回区间内。

修改为精确、可保留包围的内部表示；显示字符串不能参与数学计算。

分页注意力的空分片： 当前一个模块用 `LSE=+∞` 表示空结果，另一模块把它当真实 log-mass 参与合并。正确的“非空分片＋空分片”反而得到完全无用的无穷区间。

应定义共同的部分结果语义，显式表示空质量；只在与特定引擎交互的边界转换 sentinel。

验收： `1/3` 始终包含于权重区间；非空加空保持原结果；全空按声明的约定处理；所有状态和区间序列化往返保持其保证。

### 5. 检查器必须真正判定正确性，而不是打印报告后照样成功

优先级 P0 · 涉及 `check_v25.py`、`contract_check.py`、`run_all.sh`

这是目前最明显的准入漏洞。我在本轮再次执行了原审查脚本，确认：

- 把一个 expected 改成错误值，报告显示 contradiction，进程却退出 0。
- 把一个替代读法改错，仍可显示 `54/54 established`。
- 基础测试实际失败时，顶层脚本也可能因为管道吞掉退出码而返回成功。

这意味着目前的 `established` 不是可信的认证状态。

必须修改的内容很明确：

| 代码位置                     | 修改要求                                       |
| ------------------------ | ------------------------------------------ |
| `check_v25.py` 第 61–85 行 | 条款的所有必需样例、适用读法都参与结果聚合                      |
| 第 63–64 行                | 不得将所有 `SpecNotEstablished` 或执行异常笼统转成数学无定义  |
| 第 33–38 行                | 去掉隐藏的 `1e-40` 容差对严格包围的认证作用；经验相容性另设标签       |
| 第 70–76 行                | 误读因异常不能运行，不等于误读被数学证据拒绝                     |
| 脚本结束处                    | 任何必需检查出现矛盾或实现错误，返回非零退出码                    |
| `run_all.sh`             | 不允许 `python \\| tail` 掩盖真实测试失败，必须核对每个子进程状态 |

同时修改 `established` 的含义。

样例通过只能表示“该样例与参照相容”。

合同经来源审阅、实现经独立核验、具体查询满足使用条件，应当是不同状态。不能由一个计数器自动升级。

验收： 故意写错预期值、遗漏输出、损坏读法、让子测试退出9，都必须导致总检查失败；正常对照则不能误报。

## 二、以上修完，第三关还差什么？

### 6. 证明一份规格确实对应被检查的 Triton kernel

优先级 P1 · 涉及 `coverage.py` 及后续 audit 的任务绑定接口

当前最重要的覆盖误解，就在这里。

`coverage.py` 用正则表达式匹配 kernel 家族名称。例如名称中有 paged 或 cache，就可能找到分页注意力合同。

但名称匹配不能证明：

- 该 kernel 执行的是分页读取还是缓存写入；
- mask、scale、布局和状态更新采用哪种 profile；
- 是完整任务还是其中一段计算；
- 是否检查了全部输出与内存写回。

因此，当前 219/344 只表示找到候选合同，不是219份真实 kernel 语义已经得到认证。

必须把覆盖拆成三个独立结果：

| 覆盖阶段 | 通过要求                          |
| ---- | ----------------------------- |
| 候选匹配 | 找到可能对应的数学合同                   |
| 合同绑定 | 输入、参数、前态、输出、后态及 profile 已完整对应 |
| 参照可用 | 当前范围内能可靠求出指定保证的答案             |

对于一个融合、多启动或原地写回的计算，允许绑定到明确的计算区域，不必强迫“一个 kernel 等于一个 ATen 算子”。

为什么必须改： 如果 kernel 绑定错了，再严格的数学参考答案也只是在比较两个不同任务。

验收： 给出能够成功绑定的真实例子，也必须给出名字匹配但语义不匹配、输出缺失或状态缺失的拒绝例子。

没有绑定完成时，不允许输出 \\(G-f\\) 的语义错误结论。模式 A 的 \\(K-G\_\pi\\) 仍可独立使用。

## 三、最后一项：还缺什么，才能真正说服审稿人？

### 7. 从“开发检查通过”提升为“独立规格可信性证据”

优先级 P1 · 涉及证据目录、合同状态与生成报告

我们不是要再重新证明所有数学运算，而是让审稿人能够验证这三个事实：

第一，规格不是根据待检测 kernel 的结果写出来的。

每个启用的数学合同必须有冻结的任务依据。可以来源于标准、论文公式、用户明确采用的逻辑程序；参考实现可以作为证据，但必须标明是否同源。

第二，参照实现确实兑现了规格。

独立手算、不同算法的复算、边界和状态组合检查、误读变异都可以支持这一点。

但仅在同一个 `spec_*.py` 上检查其自身的关系，不能独自认证它符合外部任务定义。

第三，它在真实 kernel 上具有多大有效覆盖。

应使用冻结后的真实实现集合，保留全部拒绝、部分、超预算和未知项，报告实际完成了多少绑定和可靠参照，而不是从文件数量或名称匹配率推导覆盖。

这三项证据对应的是来源独立性、语义忠实性和现实适用性。它们共同支撑“可信”，但各自不能替代另外两项。

## 四、我建议直接修改现有文档里的几句关键表述

这很重要，因为当前包的 README 会把开发状态说得过强。

| 当前表述                                | 建议替换为                                                       |
| ----------------------------------- | ----------------------------------------------------------- |
| “14份合同，54条条款全部成立”                   | “14份合同已完成草案和开发测试；正式认证以来源审阅、实现核验和完整检查为准。”                    |
| “28,507项性质核对全部通过”                   | “28,507次性质测试实例通过，支持对应测试范围内的相容性，不构成28,507项独立数学证明。”           |
| “344个分族中219个落到合同”                   | “344个分族中219个找到候选合同；完成语义绑定与参照认证的数量另行报告。”                     |
| “672/797已有定义，覆盖84%”                 | “453个已有参考程序与219个新增候选映射属于不同证据级别，不能直接合并为可信 ground truth 覆盖率。” |
| “条款来源含标准／论文即 meets task definition” | “只有当前任务明确采用相应语义，且每项必要决定都获得依据并通过核验时，才能声称符合该任务定义。”            |

特别建议在 `METHOD.md` 中固定下面这一条准则：

> Specification 的可信性是相对于具体语义合同及其声明范围的条件性保证，而不是整个角色名称的属性。合同来源决定正确性目标；参考求值器及其验证决定答案的可靠性；与被审程序的绑定决定该答案能否用于此次裁决。

这句话比“我们覆盖了多少个算子”更适合作为论文规格章节的中心论断。

## 五、究竟还差多远？

我把它分成三个里程碑，不再添加新研究方向。

| 里程碑       | 当前情况                              | 达成后能说什么                              |
| --------- | --------------------------------- | ------------------------------------ |
| M1：可信执行基础 | 未完成。存在错误退出码、错误包围、状态和输出遗漏          | “参照执行器在声明保证下没有已知未隔离反例，检查器能正确传播失败”    |
| M2：可信合同来源 | 部分完成。多数内容有文献基础，但完整算法、子计算和合法变体仍有混淆 | “启用的合同具有明确来源、版本和任务选择，语义决定可追溯”        |
| M3：真实使用认证 | 未完成。219 项只是候选映射，尚缺真实语义绑定及独立验收     | “在固定真实工作负载集合中，有多少规格可以可靠用于 Triton 审查” |

M1 与 M2 完成之后，我会认可“我们建立了一套可信的 specification 生成和求值方法”。

M3 再完成后，才能有证据地说“这套方法对真实 Triton kernel 具有广泛适用性”，并给出具体覆盖比例。

至于“所有真实情形全覆盖”，即使三项完成也不应该宣称。合法的实现约定、硬件特定行为和新的算法设计不可能被一个固定目录一次性穷尽。我们真正应该争取的是覆盖范围可核算、没有证据时不误报。

## 六、接下来 Codex 应按什么顺序执行？

建议严格采用：

1. 恢复唯一审阅入口，修复检查器假通过。这里未完成之前，任何新增测试数量都不作为准入成绩。
2. 修完整参数、状态、维度和输出关系，再修严格区间及空分片组合。所有已知反例必须先失败、修后通过。
3. 逐项审定语义来源与合法 profile，区分完整任务、子计算和实现约定。
4. 最后接真实 Triton 绑定，按候选、绑定、可用三个阶段重新计算覆盖；使用冻结后独立材料验证。

我没有要求 Codex 继续扩大14份合同，也没有要求推翻我们现有 DSL。这次应当做的是把已经确定的语义方法兑现为可靠、可追踪、可以拒绝错误输入和错误判断的实际系统。

最终回答你的问题：我们离一个有说服力的 specification，不是还差一门新理论，而是还差这三道门的证据真正闭合。第一道已经有较好的基础；第二道还有确定错误；第三道仍主要停留在名称映射。把这三件事做实，比继续增加数千条通过测试更能说服审稿人。

本次文件级依据及复现可参考10月16日规格审查报告。

# 直接差分基线：运行前的预测（2026-10-06，计划 WP3 第一行）

运行前提交，结果出来后不改本文；结果与逐条核对写在 `docs/baseline_direct_diff_20261006.md`。

## 比较对象

同一批 OpInfo 用例（onesample 1440 个、放宽容差 210 个、前向全量 773 个）、同一输入（同一用例构造、同一 9 个种子、
反向用例同一上游梯度）、Dynamo 每个用例重置：

- **CI 式直接差分**：编译 fp32 对 eager fp32，`torch.testing.assert_close(rtol=1.3e-5, atol=1.5e-5, equal_nan=True)`，
  加 `test_torchinductor_opinfo.py`（v2.10.0）里 CUDA float32 的逐算子覆盖（`atol`/`rtol`/`check_gradient`）。这是"PyTorch
  CI 如果跑了全部样例"的反事实；CI 实际对 onesample 算子只跑第一个样例，单列。差异：CI 的上游梯度归一化为单位范数，
  我们沿用工具用例的上游梯度（未归一化），绝对容差因此相对更宽松一些。
- **高精度直接差分**：编译 fp32 对 eager fp64，逐输出记录相对 RMS 与最大误差，按 1e-3、1e-5、1e-6 三档标记。
- **完整工具**：已有结果（e_num、e_sem、e_total、区间证实、规则与检测器、分档）。

## 预测

1. **规格错误：直接差分全部能发现已登记的 OpInfo 问题。** B010（avg_pool1d/2d ceil_mode 反向）、B014（编译崩溃）、
   B015（avg_pool3d 反向）、B016（scatter_reduce 0 维样例的 mean 系数与 amax/amin 的 inf/NaN）在 CI 式差分下都失败。
   工具在这些案例上的增量不在"发现"，而在：区间证实（排除舍入解释）、e_num 与 e_sem 分开（kernel 忠实执行了错误的
   算法）、逐元素与逐 kernel 定位。
2. **规格一侧的误报：CI 式差分不报 `normalize_5`、`rms_norm_2`，高精度差分与工具都报。** 这两项的偏差来自 fp64 规格
   本身（0 维的精确导数为 0；eps 取 `finfo(dtype).eps`），用 fp32 eager 作参照时两边一致。即在这类情况下，以 fp32
   eager 为参照的简单方法需要人工排除的警报更少。
3. **容差以下的系统偏差只有工具报。** "小"档（插值、p-范数，1e-7 量级）与常数取整级的条目，CI 式差分全部通过，
   高精度差分在 1e-6 档也基本通过（相对 RMS 低于 1e-6）；工具报"小"或"常数取整级"。它们是否有用要看能支持什么判断
   （例如确认 Inductor 的坐标比例常数按 fp32 取整，不是 bug），不自动算作优势。
4. **补偿档（中间差异大、总差小）：** 两种直接差分都不报；工具的 e_sem 单独看会报，加上 e_total 后归入"补偿"档。
5. **覆盖：** 工具判不了的（masked.* 等参照未建立、`__rpow__` 反向）直接差分照常给出结论，这是直接差分的覆盖优势。
6. **成本：** 直接差分每个用例的耗时比工具低一到两个数量级（工具的主要开销是逐 program 的区间求值）。

## 判定口径

一个用例"被直接差分发现"指 9 个种子中至少一个失败（与 CI 一致：任一样例失败即测试失败）；按输出与用例两级统计。
规格错误与系统性作用两类问题分开报告，不汇成一个总检出数。

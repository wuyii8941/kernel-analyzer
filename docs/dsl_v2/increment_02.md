## 1. 选这几组的理由

- W1 要求每个支持签名都有正例、边界、违反前提三类测试，并有实际触发证据。按这个标准，契约基线是 **0/399**：有触发证据的 61/399，
  有真正触发了的违反前提测试的 10/399。全套测试 1843 条里，只有 71 条在本进程内调用了求值器。
- 普查本地缓存的 13,199 个 3.6.0 kernel（按内容去重；不是语料 B），按操作名被挡住的只有 2 个（`tt.atomic_cas`）。
  所以「按名字补操作」不是首要缺口；首要的是让已支持的规则有可核验的证据，并接通统计。

## 2. 目标与做法

| 项 | 内容 | 状态 |
| --- | --- | --- |
| A | 求值器的触发追踪（`KA_TRIGGER_TRACE`）：记录每个测试实际执行到的「操作:内部规则」，以及归约、扫描、原子、外部符号、内联汇编走的子路线 | 已实现 |
| B | `scripts/dsl_v2/build_rule_contracts.py`：按 rc3 schema 逐条生成契约。精度如实写为 enclosure-only（端点是 float64，不满足命题 C）；缺的测试种类留空；只用通过了的测试作触发证据 | 已实现，基线 0/399 |
| C | 有界路线（端点截断到 [−M, M] 后用 Hoeffding；M 由用户声明，不从样本取；s = 0 也能用），以及每条规则的最小可检出效应。只附加字段，不改冻结的判断 | 已实现，4 条测试通过 |
| D | 逐签名测试运动：给每个算术、比较、转换、初等函数和 libdevice 签名生成三类小用例，只编译不启动，在 CPU 上求值，再与 mpmath 高精度参考值核对包含性 | 登记后实现 |
| E | 用 conda gcc 11.4 编译官方 Triton `e50b186e`，导出构建期注册，然后跑 rc3 的核账工具 | 编译中 |

## 3. 预算

D 约半天；E 的编译约 1 h，注册导出另需半天。超过一倍先报告。

## 4. 预期（运行前写定）

- **D**：
  - 至少 80% 的支持签名得到三类测试和触发证据。剩下的预计是这几类：TTIR 前端不会生成的签名（例如部分 libdevice 的 f64 变体、
    3.6.0 前端不出现的方言操作）、`launch sequence` 这类非操作条目、需要特定布局的结构操作。
  - 包含性违反预计为 0。若出现，记为缺陷并修复（参照 SumK 的处理），修复前不计入完成。
- **E**：
  - 构建注册里的 Triton 方言操作，预计与 TableGen 源定义（215 项）一致或只有可解释的差异。
  - 上游 MLIR 方言要另行列出。编译日志在审阅方给出语料 B 之前只能用官方测试和教程，所以核账仍会是 INCOMPLETE。

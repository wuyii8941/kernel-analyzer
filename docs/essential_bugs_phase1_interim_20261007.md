## 1. 本轮问题的回答（带分母）

单位是（条件 × 候选 × 前向 / 反向）。候选只用 PyTorch 自身的实现（偏离第 5 条）：eager CPU float64 / float32、eager CUDA
float32、Inductor CUDA float32、nightly 2.15.0.dev20260907 eager / Inductor CUDA float32（受裁决），以及 CE 的 eager / Inductor
bfloat16（只记录数值差，FR 照常判）。

- **H1（存在共有错误）：成立。** B020：`scatter_reduce` / `index_reduce` 的 amax/amin 在 `include_self=False` 时，反向把被排除的
  self 计入并列分摊，源梯度变小（最小例子 0.5 对 1）。所有 eager 构建（CPU、CUDA、nightly）与 Inductor（2.10 与 nightly）一致地
  算错，50 / 602 个 index 条件。B021 的 CPU 部分在 CPU 的 float64 与 float32 之间「共有」（同一 kernel），CUDA 1d/2d 正确。
- **H2（独立规格能发现、eager 差分不能）：成立。** B020：F 50 / 50 个条件；FR 在 Inductor 的反向 kernel 上给出语义差异（e_sem
  区间不含零，非舍入）；E 0 / 50；FP64 参照（eager CPU float64）0 / 50。
- **H3（不依赖参照的性质能发现一部分）：成立，部分。** B020：并列集合的次梯度检查在 28 / 50 个条件发现（参与值本身有并列时）；
  其余 22 个条件（参与值无并列、只是被排除的 self 等于结果）预注册的性质没有覆盖。B021：梯度总量性质 2 / 2 个条件发现。
- **K_R（FR）在独立规格之上增加了什么：** F 组按主协议不判 bf16；FR 的 e_sem 与精度无关，对 CE 的 bf16 Inductor kernel 给出
  「489 个单位全部没有语义差异」——bf16 的数值差全部是舍入。在有共有错误的地方（B020），FR 把 Inductor 反向 kernel 的偏离归为语义
  （64 个条件），不是舍入。FR 与 F 的交叉：FR 从不在 F 相容的单位上报语义差异；F 发现而 FR 没有给出判断的 35 个 index 反向单位，
  偏离落在不由 Triton 写出的输出（ATen 回退）或 K_R 未建立的元素上。
- **零结果照报：** 交叉熵在全部有定义的条件上，所有受裁决的候选都与主解释（R_A + D2 分母）相容；能区分 R_A 与 R_C 的 17 个
  条件上一律是 R_A，另 38 个条件在 τ₃₂ 下区分不了。池化前向全部相容（avg 按 R2，NaN 按 R_prop）。index/scatter 前向除 B016 外全部
  相容。

## 5. 三栏结果（主协议第 6 节）

1. **文档明确条款的违反**：B021（−∞ padding 的窗口没有输入参与，却路由梯度）；B020（`include_self=False` 时 self 不参与，反向
   却按参与计数）；Inductor avg_pool 反向不是自身前向的导数（伴随性质被违反，与采用哪种除数读法无关）；B016。
2. **声明解释下的差异**：前向没有读法分歧（CE 全为 R_A，avg pool 全为 R2，NaN 全为 R_prop）。Inductor avg_pool 的反向单独看与
   R1 相容（同时列在第 1 栏）。
3. **未定义情形的实现约定**：CE-A3（分母为零）的 74 个 seed 级情形，8 个候选的 loss 一律为 NaN，梯度在 eager CPU float64 中
   18 个全零、6 个 NaN；几何空窗口的返回下标：eager 为越界位置（1 / 2 / 3），Inductor 为 −1。

## 6. 需要人来判断（上报，不自行决定）

1. **MaxPool1d 的 ceil_mode 输出长度**：2.10 文档的公式与 main 不同（见执行协议偏离第 4 条）；15 个条件已测量但暂停分类。
2. **max pool 中隐式 −∞ padding 与真实 −∞ 输入并列**：规格只把真实位置计入并列集合；Inductor 返回 padding 下标 −1、该窗口的
   梯度不路由（3 个条件），eager 返回真实位置。文档只说 padding 是 −∞，没有规定这种并列；按主协议这属于规格歧义，暂不记为错误。
3. **数值差异的统计**：任务文本要求「平均作用统计 + 已标定的 δ」，主协议第 5 节规定 3 个 seed 不用于总体宣称；第一阶段按主协议，
   第二阶段是否做，请审阅决定。
4. **P 清单的扩充**：B020 有 22 个条件只有「梯度总量 = 上游」这条性质能发现，它不在本轮预注册的清单里；第二阶段是否加入。
5. **上游提交**：B020、B021 的草稿；B015 对 #198119 的补充评论（3d 也错）。

## 7. 工具与流程本身的问题

- 工具缺陷：`kernel_analyzer.check.run` 用存储地址把输出与 Triton 写过的缓冲区配对；当输出由 ATen 回退生成、而缓存分配器复用了
  已释放的 Triton 中间量的地址时，输出被配给该中间量。两种表现：大小不同时 IndexError（6 个 3-D max pool 条件），大小相同时把旧缓冲区
  当作输出（工具自己标出「Triton 最后一次写之后被修改」，但第一个 seed 偶然通过一致性检查）——FR 评分已把工具标出的输出记为「未建立」
  （池化 2 个、index 16 个输出）。检测器冻结，未修。
- 执行中修正的程序错误（都在结果使用之前，见执行协议第 12 节）：CE 上游梯度用了加盐的 `hash()`（全部重跑）；设备端断言污染进程
  （隔离重跑）；性质检查的前提与精确性（4 处）。每一处都有对应的保护或复核。

## 8. 局限

条件小（CE 的类别数 ≤ 4099，池化与 index 的尺寸为个位数）、每个条件 3 个 seed；没有做 W5 的系统审查；实现的前后向自一致性
（`torch.func.jvp`）没有运行；nightly 的 CUDA 构建是 2.15.0.dev20260907（cu126 通道之后没有新构建），最新 CPU 构建是 20261005；
FR 只覆盖 Inductor 生成的 Triton（index 前向 378 个条件不是 Triton，池化 6 个条件工具报错）；规格只覆盖第一阶段的三个切片，
embedding_bag 没有规格。

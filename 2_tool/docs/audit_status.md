# 审查工具：阶段状态与下一步（2026-10-22）

本文是审查入口（`reference_eval/audit.py`）这一阶段的结论汇总：能做什么、证据在哪、讨论中定下的判断、仍不足的地方与下一步。
证据的原始记录在各实验目录，本文只汇总并给出出处。

## 1 现在能做什么

一次调用审查入口，对这次启动自动完成下面各项：

```python
audit(lambda: kernel[grid](...), spec=..., reference=..., names=..., programs=None | "all" | [...])
```

- 事前预测（kernel 不运行，可选）；
- 逐位核对：仿真器在 CPU 上按锁定的下降规则重算，与设备输出逐位比较；
- 精确参照 G（声明程序的精确值），实测偏差 K − G，显著性（统计显著且超过输出格式的单位舍入）；
- 给了参照程序时（通常是 kernel 替换掉的 torch 运算，float64）：逐元素比较 G − S，报告一致 / 不一致 / 无法判断、超出的元素数与
  所在 program；参照程序无定义的元素与 kernel 的非有限输出分开计数；
- 常用容差检查分三类：会通过（偏差被漏掉）、因为偏差而报错、去掉系统分量也通不过（随机误差已超出）；
- 归因：每个舍入位点逐个设为精确、各仿真一次，得到贡献，对到源码行与机制；
- 改法：按机制给出改法与代价，以及「只改一处」「全部都改」的模型内效果（后者一次同时仿真算得）；
- 各 program 偏差的范围（差别超出随机误差时提示抽样不一定代表整个 kernel）；
- 做不到的部分写「无法判断」与原因。

报告先给作者摘要，技术细节在附录。

## 3 讨论中定下的判断

- **事前预测**：对「审查自己的 kernel」不是必需的。偏差大小来自实测，工具理解是否正确由逐位核对证明，归因与改法效果用的是
  逐位核对过的仿真器。预测保留为可选的自检与研究用途（组合研究的结论不受影响）。审查默认是否关闭预测待定。
- **预测器性能**：剖析显示约一半时间花在精确 dot 的严格区间包围（DotK），预测只需要点值。可用「快速路径加可证明的回退」
  （便宜区间里没有任何 ≤ 25 位有效数字的数时直接用，否则回退）去掉，结果与精确算法的舍入决定相同。预测既为可选，此项降为低优先级。
- **归因的成本**：每个位点一次完整仿真（flash attention 6 个 program 约 4–7 分钟），一次审查可以接受；问题在于不可复用。
- **文献方向**（凭记忆，未逐条核实）：
  - 反向 / 切向一遍得到全部位点贡献（Linnainmaa 1976、Langlois 的 CENA、ADAPT、CHEF-FP）适合本工具；
  - 随机舍入 / 蒙特卡罗算术会抹掉要测的偏差，不适用；
  - 静态误差界（Fluctuat、FPTaylor、Daisy、PRECiSA）给不出偏差；
  - 概率误差分析（Higham–Mary 等）可作理论层的闭式摘要。
- **规格分两层**：DSL 定义 G（代码字面上算什么），规格库定义 f（本来应该算什么）。精度审查只用 G；规格库只影响语义判断。
  规格内容按官方文档或原论文推导；审阅方负责裁决歧义与保证独立性，不是内容的来源。
- **单个原语**（原语表）：加减乘、fma、转换都正确舍入。默认写法里的偏差来源是：
  - fp32 的 `tl.dot` 默认 tf32，操作数被截断；
  - 近似数学函数（`tl.sqrt`、`tl.exp`、f32 除法等）有零点几 ulp 的偏差；
  - 次正规数默认冲零；
  - 一个真错误：浮点取模，B024。

  实践中更大的偏差来自组合（循环里的低精度累加、窄化）。

## 4 当前不足

Specification 现在能把任务来源、参照求值和真实调用对应分开准入，也能对不支持范围明确拒绝。它不可能预先覆盖所有新算子，但对当前研究已不是主要瓶颈。
真实案例遇到缺失公式、参数、状态、输出或参照计算能力时再定向补齐，不再将规格数量当成主要成绩。

当前的主要缺口是 **bias 定位还不够适合真实修复**：

1. 现有数值定位以单个 IR 位点为单位，逐个把它改成精确计算并重跑完整仿真。这在小 kernel 上能找到相关行，在节点多、多个误差相互抵消或放大时成本很高。
2. “把一个节点设为精确”是分析反事实，不一定对应能编译、能在目标硬件上运行的源码修改；因此它不能单独支撑修复建议。
3. 定位边界还停在单个 kernel。真实算子可能包含多个 Triton 启动、非 Triton 生产者、前后态和后续算子，局部差异是否传到最终量目前不在同一条证据链中。
4. 语义差异可以在 `G−f` 上被检出，但还缺从受影响的输出回到源码公式、mask、除数、状态写入等实际原因的通用定位。
5. 当前有大量受控公式注入能证明检出和绑定正确，但缺一个同时完成“自然差异、自动定位、真实修复、后续效果”的标志性案例。

外部独立验收和其他 Triton/硬件版本仍是重要限制，但不是下一轮的首要任务。

## 5 下一步：定位、修复和传递

验收条件在实现或实验前登记，结果按成立 / 不成立 / 无法判断报告。

### 5.1 定位的输出必须能指导修复

对一个已检出的差异，定位过程先判断它属于哪一段：

- `K−G`：设备执行相对程序声明的数值差异；
- `G−f`：程序公式、参数、mask 或状态转移与任务不同；
- 输入、输出、别名或前后态对应问题。

然后从受影响的输出或状态沿实际数据流回溯，按源码表达式、归约、状态写入或 kernel 阶段对相关 IR 节点分组。报告至少给出：

1. 受影响的公开输出或后态，及其差异大小和方向；
2. 排序后的源码区域，以及每个区域到受影响输出的数据依赖；
3. 具体机制，例如低精度累加、常数舍入、边界窗口除数、mask 或写回范围；
4. 可执行的源码修复候选和预计代价；
5. 真实改写、重新编译和重测后的核验结果。

逐 IR 节点精确化可作为证据或回退，但不再作为定位的最终产物。可以使用切向传播、分组干预和区域缩减来降低成本；若线性近似不能重现完整差异，必须明确回退或报无法判断。

### 5.2 首个标志性案例

两条路线至少闭合一条：

- **bias 传递**：在发布实现的常用配置中找到未植入的局部 bias，固定输入与其他运算，只替换已定位的原因，观察它是否传到后续激活、梯度、参数更新或推理输出。传递方向或范围在确认数据前声明，局部修正必须同时减小局部和下游差异。
- **主流算子真实问题**：在主流框架的发布实现和正常参数上建立完整任务差异，定位到源码机制，做真实修复并在独立形状/输入上复验。

首选开发案例是 PyTorch Inductor `avg_pool2d(..., ceil_mode=True)` 反向。它已有完整的公开任务、前向/VJP 绑定和自然梯度差异，因此新工作不需要重新发明参照。它应用来验证：

1. 不把已知源码原因作为定位器输入时，报告的区域和机制是否命中；
2. 修复边界窗口除数后，梯度 `K−f` 是否消失，前向和其他梯度是否保持正确；
3. 另一组尺寸和参数是否也通过，避免只修开发用例。

该案例闭合后，再在带后续算子的训练或推理路径上做 bias 传递实验。如果 `avg_pool2d` 不适合承载传递主张，它仍可完成“主流算子真实问题”路线，传递路线另选已有自然数值 bias 的归一化、注意力或优化器调用。

## 6 当前结论边界

- 现有规格与调用绑定足以开始上述工作；这不等于已经定义所有未来算子。
- 已植入的 `+0.25`、mask 翻转等例子是检出能力回归，不能代替自然案例。
- 只有输出差异或一个 IR 节点排名，还不能声称已经修复。
- 一个微 kernel 的 bias 不自动证明会影响训练或推理；传递性必须在明确的后续路径上单独测量。
